# Протокол проверки FoodExpress

| Параметр | Значение |
|---|---|
| Дата проверки | 15 ноября 2026 |
| PostgreSQL | 18.6 |
| Исходная БД | `foodexpress_dev` |
| БД для восстановления | `foodexpress_restore_full` |
| Схема | `udovenchuk_food` |
| Роль для функциональных проверок | `inspector` |

## A. Восстановление архива

В `foodexpress_dev` установлены скрипты `01–14`. Архив в формате Custom содержит структуру схемы `udovenchuk_food`. Список объектов архива подтверждает отсутствие записей `TABLE DATA`.

```bash
pg_dump -Fc --schema-only --no-owner --no-acl -n udovenchuk_food \
    -d foodexpress_dev -f db/foodexpress_udovenchuk.backup
```

Архив восстановлен в чистую БД с подготовленными схемой `exts` и расширением `uuid-ossp`. Определения восстановленных объектов совпали с результатом отдельной установки скриптов `01–14`. После восстановления администратор выполнил `db/schema/grants.sql`.

## B. FOOD-101. Структура схемы

В восстановленной схеме обнаружены 12 таблиц из ERD, 8 enum-типов, 16 внешних ключей и 8 триггеров проекта. Поля идентификаторов имеют тип UUID. Генерация UUID через `exts.uuid_generate_v4()` работает под `inspector`. Обоснования ограничений приведены в [constraints.md](constraints.md).

## C. FOOD-102 и FOOD-103. Генерация и очистка

После восстановления под `inspector` дважды выполнен `CALL udovenchuk_food.insert_test_data(10)`. Второй вызов добавил ещё столько же записей.

| Таблицы | Первый вызов | Второй вызов |
|---|---:|---:|
| `client`, `courier`, `restaurant`, `product_category` | 10 в каждой | 20 в каждой |
| `address`, `product`, `order`, `order_structure`, `payment`, `review` | 50 в каждой | 100 в каждой |
| `client_address` | 40 | 80 |
| `courier_pay` | 60 | 120 |

Два вызова `erase_test_data()` подряд прошли. После каждого все 12 таблиц содержали 0 строк. После повторного заполнения снова получено 50 заказов.

## D. Правила на тестовых данных

Стоимость блюд совпала с суммой позиций заказа. У каждого сгенерированного заказа была одна успешная оплата на полную сумму. Даты создания и окончания доставки прошли проверку. Выплаты за шесть месяцев совпали с произведением сохранённых коэффициентов на сумму комиссий доставленных заказов. Рейтинги блюд и ресторанов совпали со средними по отзывам с округлением до сотых.

## E. Функции и процедуры

### FOOD-104. Добавление блюда

`add_product(...)` добавил по одной записи с фото и без фото. UUID присвоен автоматически. Вызовы с несуществующим рестораном, несуществующей категорией и отрицательной ценой отклонены с ожидаемыми сообщениями. После ошибочных вызовов количество строк сохранилось.

### FOOD-105. Пересчёт рейтинга

| Действие | Фактический результат |
|---|---|
| Добавление оценок 3, 4 и 5 одному блюду | Рейтинг 4,00 |
| Удаление оценки 3 | Рейтинг 4,50 |
| Изменение оценки 4 на 3,5 | Рейтинг 4,25 |
| Перенос отзыва между блюдами и с блюда на ресторан | Пересчитаны оба затронутых объекта |
| Удаление последнего отзыва или его перенос на заказ | Рейтинг прежнего блюда или ресторана стал `NULL` |

### FOOD-106. Статистика ресторанов

```sql
SELECT * FROM udovenchuk_food.get_statistic();
```

Получены пять колонок `restaurant_name`, `best_product_name`, `total_amount`, `avg_amount`, `best_user` и 10 строк для 10 ресторанов. В отдельном сценарии после добавления ресторана без заказов получены 11 строк, у нового ресторана суммы и лидеры равны `NULL`. Добавленный в существующий ресторан крупный заказ со статусом «создан» не повлиял на результаты. Суммы, средние и лидеры совпали с отдельным расчётом по доставленным заказам. Для клиента возвращается логин.

### FOOD-107. Зарплата курьеров

`CALL udovenchuk_food.courier_salary()` выполнен дважды под `inspector`. За текущий месяц сохранилась одна запись на курьера. При неизменных заказах суммы и применённые коэффициенты совпали после обоих вызовов. Ставка следующего месяца определяется по количеству доставок.

## F. FOOD-108. Финансовый отчёт

```sql
SELECT * FROM udovenchuk_food.how_much_money ORDER BY year_month;
```

Получены 8 колонок в порядке из задания. Тип `year_month` — `text`, остальных колонок — `numeric`. Результат содержит 6 последовательных месяцев от `2026-06` до `2026-11`. В августе суммы заказов, комиссия, выплаты и прибыль равны нулю. В июне `prev_commission` и `commission_diff` равны `NULL`.

Суммы сверены с таблицами заказов и выплат. Например, в ноябре комиссия равна `56855.70 − 51687.00 = 5168.70`, выплата — `516.87`, прибыль — `4651.83`. Предыдущая комиссия и разность комиссий сверены для каждого месяца. На пустой базе представление возвращает 0 строк.

## G. FOOD-109 и FOOD-110. Права и проверка полной версии

Подключение к восстановленной БД выполнено с логином `inspector`. `current_user` подтвердил роль. Проверены права `USAGE` и `CREATE` на `udovenchuk_food` и `USAGE` на `exts`, `information_schema` и `pg_catalog`.

Запросы к `information_schema.tables` с фильтром `BASE TABLE` и к `pg_catalog.pg_tables` вернули по 12 таблиц. Под `inspector` выполнены `insert_test_data(10)`, `erase_test_data()`, `add_product(...)`, `get_statistic()`, `courier_salary()` и чтение `how_much_money`. Ошибок доступа не было.

## H. План запроса статистики

`EXPLAIN ANALYZE` для SELECT из `12_get_statistic.sql` на 50 заказах показал один проход таблицы `"order"` в CTE `delivered_orders` (`loops=1`). Промежуточная выборка использована для сумм, лидеров по блюдам и лидеров по клиентам. Время выполнения в этом прогоне — 0,308 мс.
